# Rustify PortableApps Builder Kit — b1r1 (unofficial)

A standalone Windows GitHub Actions builder for **https://github.com/PabloSoage/Rustify**. **Selected architecture: PORTABLEAPPS only.** It retrieves the upstream author's verified portable Windows x64 ZIP (rather than recompiling the entire Kotlin/Rust desktop), compiles a genuine C++ PortableApps root launcher, redirects native Rustify portable profile storage to `Data`, builds and validates a ready-to-extract ZIP, creates a separate **PortableApps-style custom-NSIS installer** through the shared pinned package builder, then uses the pinned shared Release Publisher. **No compiled Rustify/installer binary is included in this kit.** They are generated by GitHub Actions.

## Beta release workaround — how to choose a version

Rustify currently publishes **beta** desktop releases, not stable Windows portable releases. For this requested project, `beta` is the clearly labeled manual-workflow default; it is NOT silently treated as stable.

| `release_channel` | `release_tag` | What happens |
|---|---|---|
| `beta` | *(blank)* | Automatically selects highest numeric beta version that has an official Windows x64 portable ZIP. Start here. |
| `beta` | `v5.6.4-beta` | Pin exactly that beta. Checks the tag is published, in the beta channel and has a verified Windows ZIP. |
| `stable` | *(blank)* | Select latest true stable Windows portable ZIP once the developer publishes one; otherwise intentionally stop with an explanation. |
| `stable` | `v6.0.0` *(future example only)* | Pin an explicitly published stable tag once it exists. |

There is **no** risky unverified-main bypass, generic prerelease guessing, or false 'stable' relabeling. Release versions are ordered numerically (5.10.0 newer than 5.9.0), and authentication/rate-limit/server failures are not swallowed. Both builds and repacks stop on a missing GitHub checksum or changed upstream portability contract.

## Beginner-friendly setup with GitHub Desktop

1. On GitHub.com, select **New repository**, give it a different name such as `Rustify-Portable-Builder`. Do **not** fork Rustify. Choose public or private. A private repo keeps build releases private; the source application is GPL-3.0, so follow license obligations if distributing binaries.
2. In GitHub Desktop, choose **File → Clone repository** and select the new builder repository. GitHub Desktop handles Git; you do **not** need `git init`.
3. Open the cloned repository folder. Extract this kit ZIP **into the repository root**, copying its `.github` hidden folder and everything under `scripts`, `launcher`, `assets`, `docs`, `tests`. Do not put the entire kit in a nested folder.
4. In GitHub Desktop, review all new files. Enter commit message `Add Rustify PortableApps builder b1r1`, press **Commit to main**, then **Push origin**.
5. On GitHub.com, open your builder repo → **Actions** → **Build Rustify PortableApps (official portable release)** → **Run workflow**.
6. Choose `release_channel=beta` and leave `release_tag` empty for latest beta, or put `v5.6.4-beta` to pin this known release. Leave `publish=true` if you want the ready-to-download release created automatically. Press **Run workflow**.
7. Open the running workflow and expand each step. Key steps: **Resolve**, **Download official portable ZIP**, **Compile genuine C++ launcher**, **Create ZIP**, **Build installer**, **Publish**. The summary prints ZIP hash, installer result, and release tag.
8. When successful, open your repository's **Releases** section. Download the release's `RustifyPortable_...zip`, optionally `RustifyPortable_...custom-nsis-r1.paf.exe`, and `SHA256SUMS.txt`. Confirm SHA-256 before using the package.
9. **ZIP method:** extract so the folder is `RustifyPortable\` (not two nested RustifyPortable folders), then launch `RustifyPortable.exe`. **Installer method:** run the separate `.paf.exe`, choose the PortableApps folder (or compatible USB drive) and launch `RustifyPortable.exe`. In PortableApps Platform, refresh application icons if it does not appear immediately.
10. The app saves settings, data, playlists/history, and cache in **`RustifyPortable\Data\RustifyProfile\`**. Do not delete `Data` on upgrades. The upstream profile may hold absolute paths to your chosen music library or downloads; adjust these after moving drives. Spotify login uses the host's own credential store, so you may need to sign in again on another computer.
11. **Upgrade:** build the desired newer release. Close the application including tray, back up `Data` and the last working ZIP, then install into the same folder using the shared installer (which preserves Data), or extract the new ZIP elsewhere and manually copy ONLY `App`, `Other`, and `RustifyPortable.exe` over the old copy. Never overwrite existing `Data`.
12. **Rollback:** close Rustify, restore the previous `App`, `Other`, launcher and (if new app upgraded any schemas) the matching backed-up `Data`. Never delete `.__UPB_Backup` or `.__UPB_Stage` from an interrupted installation without investigating the recovery state.

## Workflow output and retry behavior

Main workflow: `.github/workflows/build-rustify.yml`, manual only, Windows hosted runner, no local compiler, no PAT, no GUI input. A validated ZIP is **independent** of installer success. If installer construction fails, ZIP is still published when `publish=true`, and the summary marks the installer as FAILED. A retry with different output must use an intentionally changed builder/package revision or the **Repackage existing verified Rustify ZIP** workflow so already published ZIP is not overwritten.

Optional installer-only recovery: `.github/workflows/repackage-installer.yml`. Pass the exact **builder-repository** source release tag, not the upstream tag. It verifies the original source ZIP against the original publisher's `SHA256SUMS.txt`, extracts it, validates package layout, and creates a new r2 installer-only Release. It does not re-download or recompile upstream. It requires the original b1r1 release and never edits that release. Do not use it if source ZIP is from elsewhere.

`work/`, `installer-out/`, `release-out/` contain temporary build data ignored by Git. Shared publisher publishes only valid `.zip` / `.paf.exe` and creates authoritative SHA256SUMS.

## Verification scope

**Already validated locally:** Python release-resolution and archive-security unit fixtures (12 tests), actual kit file presence, source references, verified shared action interfaces and correct source-based portable controls. **Not yet verified:** actual MSVC build, official asset SHA verification in GitHub Actions, complete app ZIP, Windows GUI/data persistence, notifications, installed-app coexistence, installer execution, and release publication. The workflow performs these static/build checks when you run it; real interactive Windows testing remains a separate acceptance step.

**Operational limitations:** no automatic OS login autostart; no Windows service/driver; no broad AppData or registry cleanup; no guaranteed portable Windows Credential Manager secrets, webview caches, notifications, taskbar history or Windows-managed caches. The upstream `rustify://` registry handler is deliberately skipped in portable mode. In-app upstream updating should not be used on the portable copy. See `docs/PORTABILITY.md` and `docs/AUDIT-AND-VALIDATION.md`.
